El origen

Por qué construí esto

Mi cuñado es el responsable de una empresa de limpieza que gestiona varios centros de trabajo. Un día me comentó que le gustaría tener una app para controlar el stock: que cada trabajador, al coger un producto del almacén, pudiera notificarlo desde su móvil y a él le llegara una notificación al instante.

Me preguntó qué herramientas usaba yo para construir mis proyectos. Le hablé de OpenCode y Antigravity. Intentó hacerlo él mismo, pero no tenía los conocimientos necesarios para llevarlo a cabo.

Así nació Kavana Warehouse. Lo construí como proyecto personal, pensando exclusivamente en su problema. Podría usarse en cualquier sector, pero lo diseñé a medida para esa empresa de limpieza. Quise demostrar que podemos crear soluciones específicas, pegadas a un cliente real, y no productos genéricos que intentan servir para todo. Esa es la mentalidad de producto que quiero mostrar con este proyecto.

Lo que demuestra

Capacidades técnicas visibles en este proyecto

🏗️

API REST con Express + Prisma

Backend en Node.js 22 con Express y Prisma ORM. Endpoints para productos, almacenes, inventarios, movimientos y usuarios. Respuestas tipadas de extremo a extremo.

🔒

Multi-tenant shared schema

Aislamiento lógico por client_id en PostgreSQL 16. Todos los tenants comparten esquema pero los datos están separados a nivel de aplicación. ADR →

👥

Auth JWT + RBAC

Autenticación stateless con JWT + refresh tokens. Cuatro roles definidos (admin, supervisor, operario, viewer) con permisos granulares por módulo.

🐳

Docker 3 servicios

API, dashboard y app mobile como servicios independientes orquestados con docker-compose. Entorno replicable con un comando.

📦

Inventario multi-almacén

Gestión de productos con categorías y proveedores. Entradas, salidas, transferencias entre centros e inventarios físicos con detección de desviaciones.

📊

Dashboard con KPIs

Vista operativa con métricas de consumo, alertas de stock bajo y KPIs en tiempo real por centro y período.

📋

Trazabilidad completa

Registro histórico de todos los movimientos con filtros por fecha, almacén, tipo de operación y usuario. Nada desaparece sin dejar rastro.

🔗

API REST documentada

API diseñada para integraciones con ERPs o sistemas externos. Documentación técnica de endpoints disponible en el repositorio.

🧪

26 tests automatizados

Tests unitarios y de integración con el stack real. Ejecutables en local con npm test.

Decisiones técnicas

Criterio aplicado, no solo código

Decisiones de arquitectura que responden a restricciones reales: un desarrollador solo, un cliente concreto, necesidad de desplegar rápido y de forma reproducible.

🔒 Shared Schema multi-tenant

Todos los clientes comparten esquema con aislamiento por client_id. Simple de mantener, eficiente en recursos, y suficiente para el dominio. Para proyectos más grandes se migraría a RLS. ADR →

👤 JWT + RBAC en vez de sessions

Arquitectura stateless: sin estado en servidor, escalable horizontalmente. Refresh tokens para no pedir login cada 15 minutos. Cuatro roles con granularidad por módulo.

🐳 Docker 3 servicios independientes

API, dashboard y app separados como contenedores con docker-compose. Un comando levanta todo el stack: PostgreSQL + API + dashboard + app mobile.

🗄️ Prisma ORM en vez de SQL raw

Schemas declarativos, migraciones automáticas y type-safety desde la BD hasta el frontend. Menos errores, más velocidad de iteración.

👤 El supervisor decide quién registra, no todos los limpiadores

Primero probamos que todos los operarios lo hicieran desde el móvil, pero fue un lío: se olvidaban, se equivocaban, y el trabajo se ralentizó. Entonces cambiamos: el supervisor elige quién lleva el control. A veces él mismo lo hace. Así evitamos que el registro genere fricción y el equipo pueda centrarse en limpiar sin interrupciones.
